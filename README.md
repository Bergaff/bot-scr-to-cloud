# Telegram: постинг-радар — посылки, передачи, попутчики

Автоматический поиск в твоих чатах сообщений про передачи/посылки/попутчиков
с ссылкой на каждое сообщение, базой и уведомлениями.

Собрано на базе разбора статьи [glorycloud.com/blog/telegram-scraping-guide](https://www.glorycloud.com/blog/telegram-scraping-guide/) —
что в ней надо поправить, см. раздел «Уроки статьи» ниже.

## Что куда

| Задача | Инструмент | Аккаунт | Риск бана |
|---|---|---|---|
| **Мониторинг чатов в реальном времени** (главное) | `monitor.py` | Да | Низкий |
| Поиск по словам в публичных каналах | `web_search.py` | Нет | Нулевой |
| Разовый сбор истории канала | `scraper.py` | Да | Средний |
| Проверка правил и логики | `matcher.py`, `selftest_monitor.py` | Нет | — |

## Быстрый старт: мониторинг твоих чатов

Твои ссылки — это **группы/чаты** (`travelersminsk`, `belgranica`, `granica_es`, `granica_bypl`),
у них отключено веб-превью, поэтому читать их надо твоим аккаунтом через Telethon.
Десять источников уже прописаны в `sources.yaml` (включая приватный чат по ссылке-приглашению
`https://t.me/+CmQyl50rf-NlODFi` — он читается глубже остальных).

```bash
# 1. Один раз: окружение
cd telegram-scraper
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 2. Один раз: ключи приложения и вход в аккаунт (мастер ведёт по шагам)
./start.sh --login                # Windows: start.bat --login

# 3. Проверить, что правила и конвейер в порядке (без аккаунта, ~10 секунд)
python3 selftest_monitor.py

# 4. Проверка окружения и ключей, затем тестовое уведомление
python3 monitor.py --doctor
python3 monitor.py --test-notify

# 5. Боевой запуск: живьём, уведомления в консоль
python3 monitor.py --notify console --catchup 50
```

Мастер `--login` спрашивает `api_id`/`api_hash`, сам создаёт `.env`, показывает QR-код для входа
и определяет `chat_id` твоего бота. Ключи берутся за минуту на
**https://my.telegram.org/auth?to=apps**: войти номером телефона, название приложения — **любое**,
сохранить `App api_id` (число) и `App api_hash` (32 символа). Это ключи приложения, а не пароль
от аккаунта — по ним Telethon (и Pyrogram) говорят Telegram, какое приложение стучится.
Регистрируй приложение на свой аккаунт: «чужие» готовые ключи из интернета делят трафик со всеми,
кто их использует, и аккаунт с них слетает заметно чаще.

Ключи можно вписать и руками (`export TG_API_ID=…`, `TG_API_HASH=…` или файл `.env`) — тогда вход
по QR отдельно: `./start.sh --login-qr`. После входа работает файл сессии `monitor_session.session`:
телефон и код больше не нужны.

Что происходит: читаются последние `catchup` сообщений каждого чата, дальше сообщения
приходят пушем. Каждое совпадение: пишется в `hits.sqlite3`, печатается в консоль
и, если включено, уходит ботом.

### Уведомления

```bash
python3 monitor.py --notify console                 # в консоль (по умолчанию)
python3 monitor.py --notify file --notify-file hits.log   # в файл
python3 monitor.py --notify both                    # и туда, и туда

# сообщением в Telegram от бота (бота создать у @BotFather, свой id узнать у @userinfobot)
export TG_BOT_TOKEN=123:ABC
export TG_NOTIFY_CHAT=123456789
python3 monitor.py --notify bot
```

В уведомлении: категория (📦 посылка / 🚗 попутчик), намерение (предлагаю/ищу),
направление (`BY->PL`), счёт совпадения, текст и **ссылка на сообщение** —
`https://t.me/travelersminsk/91532` для публичных чатов, `https://t.me/c/<id>/<msg>` для приватных.
Приватные, доступные только по ссылке-приглашению, задаются как `https://t.me/+<hash>`; если аккаунт
в чате ещё не состоит — разовый запуск с `--auto-join` подпишет его (в статистике такой чат виден как `+<hash>`).

### Расписание (без постоянно висящего процесса)

```bash
# каждые 10 минут разовый проход по новым сообщениям
*/10 * * * * cd /home/user/telegram-scraper && .venv/bin/python monitor.py --once --notify bot >> monitor.log 2>&1
```

`--once` читает только то, чего нет в `seen` (дедупликация в SQLite), поэтому частые
запуски безопасны и не дают повторов.

### Бот-панель: статус и статистика в Telegram

```bash
python3 monitor.py --bot-panel --notify none --heartbeat 15   # панель внутри радара
python3 monitor.py --panel-only                              # панель отдельно (ключи аккаунта не нужны)
python3 monitor.py --check-sessions                          # живая проверка сессий (радар должен стоять)
```

В личке бота: `/status` (режим, аптайм, находки и пересылки сегодня, очередь, ошибки),
`/accounts` (**жив ли каждый аккаунт**: «работает» или «молчит 34 мин»), `/stats 7`, `/report`,
`/queue`, `/last 10`, `/usage` (память, CPU, размер базы и вердикт «A подходит / рекомендую B»),
`/errors`, `/sources`, `/top`, `/limits`, `/mode`, `/ping`, `/why <id>`, `/export`, `/digest on|off`.
Полный список — `/help` и раздел 8 в `COMMANDS.md`.

Живость считается по **пульсу** (`--heartbeat` пишет строку в базу раз в N минут), а не по
находкам: тихий чат ночью не выглядит поломкой. Панель не открывает Telethon-клиенты и не
трогает `.session` — она читает `hits.sqlite3` (таблицы `heartbeats`, `errors`, `metrics`,
`bot_state`), поэтому радар и панель работают одновременно. Команды принимаются только от
числового `TG_NOTIFY_CHAT`; бот сам шлёт алерты: «аккаунт молчит», «сессия сломана»,
FloodWait, «лимит исчерпан», утренний дайджест.

В схеме B (разовые проходы по cron или в облаке) пульс пишется в конце каждого прохода —
накопительными суммами из базы, поэтому панель видит живость и там: проходы встали, значит
будет «⚠️ молчит N мин». Панель на облачной базе запускается одной командой: `cloud_panel.bat`.

### Расход: метрики и вердикт «A или B»

```bash
python3 monitor.py --metrics-interval 15 --metrics-csv metrics.csv   # срезы раз в 15 минут
python3 monitor.py --once --catchup 0 --notify bot                   # схема B: срез в конце прохода
```

Радар сам измеряет, сколько он стоит: раз в `--metrics-interval` минут пишет срез (память,
процессор, аптайм, сколько прочитано, API-вызовы, размер базы) в таблицу `metrics` и раз в час
— строкой в `metrics.csv` (utf-8, разделитель `,`, открывается в Excel). Смотреть: `/usage` у
бота, строка `[i] расход: ...` после прохода `--once`, либо сам `metrics.csv`.

По срезам за сутки считается вердикт: `A подходит: ресурсов мало` (RSS ≤ 150 МБ и CPU ≤ 5 %),
`A возможна, но следи` (до 250 МБ / 15 %) или `рекомендую B (проходы по расписанию)`
(RSS > 250 МБ, CPU > 15 %, ≥ 3 FloodWait за сутки, ошибка сессии). Пороги — константы в
`metrics.py`. `psutil` не обязателен: на Linux и Android цифры берутся из `/proc`, без них
часть полей честно показывается как «н/д». Строки старше 30 дней удаляются сами — и из базы,
и из `metrics.csv`.

### Выгрузка находок

```bash
python3 monitor.py --export hits.txt                        # текстовый отчёт (Блокнот)
python3 monitor.py --export hits.txt --export-hours 24      # отчёт только за сутки
python3 monitor.py --export hits.csv                        # CSV для Excel
python3 monitor.py --reset-db                               # очистить базу и пересобрать заново
```

Полезные комбинации для твоих чатов (поток большой — до половины сообщений объявления):

```bash
# только те, кому нужно передать/доехать (им можно предложить услугу)
start.bat --once --notify bot --only-intent request

# только направления из Польши в Беларусь
start.bat --notify bot --only-direction PL->BY

# минимальный шум: только посылки, ищущие передачу, с высоким счётом
start.bat --notify bot --only-intent request --min-score 12

# без пассажирских объявлений (только посылки/передачи/документы/груз)
start.bat --notify bot --category parcel,mixed
```

## Как это ищет: твои регулярки -> правила

Твои два регекспа я перенёс в `matcher.py`, починив три вещи, которые в JS-варианте
дали бы мусор на реальных чатах:

| Было | Проблема | Стало |
|---|---|---|
| `груз` | ловит «грустно», «грустный» | `груз(?!ст)…` |
| `ищу` | ловит «поищу», «отыщу», «взыщу» | `(?<![а-я])ищу(?![а-я])`, и это **слабый** сигнал (вес 1) |
| `переда[мтн]` | не ловил «передача», «передай» (нет буквы после) | `переда[а-я]{0,4}` |
| — | падежи: `посылк…`, `бандерол…`, `коробк…`, `вещи/вещей` | учтены в паттернах |

Плюс добавлено то, без чего в чатах будет много пропусков и много шума:

* **намерение** — «предлагаю» (`возьму/везу/есть место/могу взять`) и «ищу»
  (`нужно передать/кто едет/ищу машину`), с весом 3: без намерения объявление не считается найденным;
* **антипаттерны** — реклама, «заявка принята», вакансии, ТВ-передачи, новостной стиль
  («Правительство Литвы продлило…»);
* **пограничный контекст** — очереди, рейсы, таможня, правила въезда: для `profile: news`
  такие посты отсекаются целиком, для `profile: chat` нужен более сильный сигнал;
* **география и направление** — «Минск-Варшава», «из Бреста в Вильнюс» → `BY->PL`;
* **категории** — 📦 посылка/передача, 🚗 попутчик/пассажир или 📦🚗 смешанные
  (водители часто берут и людей, и груз): предмет задаёт категорию, а слова-намерения
  («возьму», «везу») — только намерение;
* **дедупликация** трёх видов: по `(чат, id сообщения)`, по тексту в пределах 24 ч
  (`--dedup-window`) и **между чатами** (`--dedup-scope global`, по умолчанию) — одни и те же
  водители пишут в 3–4 чата, приходит одно уведомление вместо четырёх;
* **окно свежести** — `--max-age 24` (по умолчанию): сообщения старше N часов не уведомляют,
  но помечаются просмотренными, поэтому новая база или `--reset-db` не вываливают старые объявления;
* **фильтр по категории** — `--category parcel,mixed` (без чистых пассажирских объявлений);
  слова-намерения («возьму», «везу», «могу взять») категорию НЕ задают: её определяет предмет
  (посылка/передача/груз → parcel, попутчик/места в машине → ride); (только те, кто ищет/только те, кто предлагает)
  и `--only-direction BY->PL,PL->BY` — чтобы не тонуть в потоке;

### Несколько аккаунтов (`--account`, `accounts:`)

Часть чатов можно отдать второму аккаунту — тогда у каждого свои чаты и свой лимит пересылок,
а база (и дедупликация) общая. Запуск всех аккаунтов — обычный `python monitor.py`, одного —
`python monitor.py --account second`. Подробнее в START-HERE.md, раздел «Два аккаунта».

### Профили источников (`sources.yaml`)

```yaml
- target: "@travelersminsk"   # чат объявлений — базовые правила
  profile: chat
  min_score: 4
- target: "@granica_bypl"     # гигантский чат, много новостного фона
  profile: news
  min_score: 6
```

Подкрутка: шума много → `min_score` +1; находок мало → `min_score` −1 (ниже 4 не советую).

## Пересылка боту и статистика

```yaml
forward:
  to: "@parcel_transfer_bot"   # получатель (бот, канал или второй аккаунт)
  mode: forward                # forward = честная пересылка; copy = текст со ссылкой
  max_per_day: 180
  fallback: link               # в чатах с запретом пересылки — текст + ссылка
```

Пропуск авторов со скрытым профилем: сообщения, пересланные от пользователей, чей профиль
закрыт («hidden by user» — Telegram отдаёт только имя, без идентификатора), по умолчанию не берутся:
такому автору нельзя написать. Отключается `--keep-hidden` или `skip_hidden: false` в `defaults`.

Настройки пересылки берутся в порядке: флаг командной строки → `sources.yaml` → встроенное
значение (`forward`/`100`/`link`). Без флагов действует конфиг; флаг перекрывает его на один запуск.

В живом режиме полезен пульс — раз в N минут одна строка о состоянии (процесс жив, сколько
сообщений пришло с прошлого пульса, что с пересылкой и очередью, когда было последнее принятое
сообщение): `--heartbeat 15` или `heartbeat: 15` в секции `defaults`. Форум-чаты можно читать целиком (по умолчанию) или только выбранными темами:
`start.bat --list-topics` покажет темы и их id, дальше `topics: [502]` у источника в `sources.yaml`.

Порядок обхода чатов задаётся в `defaults.order`: `random` (по умолчанию) — каждый запуск
начинается со случайного чата, чтобы дневной лимит пересылок распределялся ровно;
`config` (или `--order config`) — строго как в списке источников.

* сутки для лимита считаются с **местной полуночи**; в долгом живом прогоне лимит обнуляется
  и очередь добирается автоматически, без перезапуска;
* что не влезло в лимит — не теряется: находка становится в очередь и уходит в следующий прогон
  (добор выполняется первым делом при запуске, пока есть свободный лимит);

* пересылает **твой аккаунт**, поэтому получателем может быть бот (нужно один раз нажать у него
  Start), канал-архив или второй аккаунт;
* каждая отправка фиксируется в базе → повторно одно и то же не уходит;
* `stats.txt` / `stats.csv` обновляются после каждого запуска: по каждому источнику видно,
  сколько прочитано, найдено, новых, переслано, отсеяно фильтрами и по возрасту.

```bash
python3 monitor.py --test-forward                # проверка: переслать боту последнее сообщение из чата
python3 monitor.py --show-stats                  # отчёт в консоль
python3 monitor.py --once --forward-to @bot      # пересылка в разовом прогоне
python3 monitor.py --once --forward-dry-run      # проверка без отправки
```

## Несколько аккаунтов (`accounts`)

Чаты можно разделить между двумя аккаунтами: у каждого свой `.session`, свой получатель и **свой
дневной лимит пересылок**, а база и дедупликация общие — одно объявление не уйдёт боту дважды.

```yaml
accounts:
  main:
    session: monitor_session
    forward: {to: "@parcel_transfer_bot", mode: forward, max_per_day: 120}
  second:
    session: second_session
    forward: {to: "@parcel_transfer_bot", mode: forward, max_per_day: 60}
sources:
  - {target: "@granica_BY_LT_PL", account: main}
  - {target: "@granica_polska", account: second}
  - {target: "@travelersminsk", account: auto}   # auto — распределить по кругу
```

* без секции `accounts` всё работает как раньше — один аккаунт `main`;
* без строки `account` источник берёт первый аккаунт;
* вход вторым аккаунтом: `start.bat --login --session second_session` (мастер) или
  `start.bat --login-qr --session second_session` (только QR);
* только один аккаунт: `--account second`; проверка конфига — `--doctor` (покажет сессии и лимиты);
* в логе, пульсе, уведомлениях и статистике появляется имя аккаунта; в отчёте — раздел
  «ПО АККАУНТАМ»;
* новое в SQLite: `account` у hits/forwarded/stats; старые базы мигрируют автоматически
  (прошлая история помечается `main`, чтобы дневной счётчик не обнулился);
* **одна сессия = один запущенный процесс**: тот же `.session` из двух мест → `AuthKeyDuplicatedError`.

## Аккуратно с аккаунтом

Чтение чатов почти не тратит лимиты: живые сообщения приходят пушем, запросы нужны только
на `catchup` и на резолв автора (кэшируется). Правила, зашитые в код:

* `flood_sleep_threshold=0` — `FloodWait` не проглатывается молча: выводим, ждём указанное
  время +20 %, после флуда поднимаем базовую паузу в 1.5×;
* пауза `--delay` (по умолчанию 2 с) + случайный джиттер между вызовами API;
* `catchup` ограничен (по умолчанию 30–50 сообщений на чат): большое «долистывание» истории —
  это уже работа для `scraper.py --mode history`, не для монитора;
* свой сеанс (`monitor_session.session`) — не запускай его одновременно с других IP;
* `--include-own` не нужен: свои сообщения пропускаются, чтобы радар не реагировал на себя;
* уведомления ботом (`--notify bot`) требуют `TG_BOT_TOKEN` + `TG_NOTIFY_CHAT`; проверка —
  `--test-notify --notify bot` (сразу скажет, что ответил Telegram на токен); при 401 уведомления
  ботом выключаются до конца прогона, а недоставленные остаются в базе — их догоняет
  `--resend-pending N`;
* пересылка ограничена `max_per_day` (по умолчанию 180) и идёт с паузой `--delay`; при
  `PEER_FLOOD` отправка останавливается автоматически; отложенное по лимиту автоматически
  добирается в следующий прогон, так что поток находок не теряется.

Если прилетел `FloodWait` — просто дай скрипту доехать, он сам выждет.
Если `PEER_FLOOD` — это уже ограничение аккаунта: останови мониторинг на сутки-двое.

1. **Версия Telethon.** Статья под v2 (до сих пор `2.0.0a0`), а `pip install telethon` даёт
   1.45.x: там `TelegramClient`, а не `Client`; `.message` удалён, работать надо с `.text`.
2. **Прокси не спасают от лимитов** — Telegram ограничивает аккаунт, а не IP. Прокси нужны
   для многих аккаунтов или при блокировке самого Telegram, а не как «антибан».
3. **`message.sender` часто `None`** — сохраняем `sender_id` и резолвим отдельно (в мониторе с кэшем).
4. **`GetParticipants` — главный путь к ограничениям.** Правильный подход к «участникам» —
   история сообщений и авторы в ней, что монитор и делает.

## Возможности для доработки

* отдельные БД у `monitor.py` и `scraper.py` не конфликтуют: `hits.sqlite3` / `out/*.jsonl`;
* теги ключевых слов уже пишутся в CSV (`hits`), можно группировать статистику
  (сколько в день, кто чаще пишет, по каким направлениям);
* если понадобится дашборд — данные в SQLite, можно навесить Metabase/Streamlit;
* хочешь — попроси, добавлю: локальные уведомления в Telegram-чат через MTProto (без бота),
  фильтр «только из моего города», ответ на найденное сообщение одной командой.

## Разбор в статье про скрапинг (сокращённо)

* Запуск: ключи `my.telegram.org` → сессия → `get_entity` → `get_messages`/история.
* Поиск по словам: серверный (`search=`) ищет по словоформам индекса и только в чатах,
  где ты состоишь; локальный фильтр по истории даёт больше контроля и морфологию.
* Бан: `FloodWait` — троттлинг (спим), `PeerFlood` — ограничение аккаунта (пауза 24–48 ч),
  `UserDeactivatedBan` — бан. Отдельный аккаунт, темп ≥2 с/запрос, никаких массовых
  `GetParticipants` и вступлений, логировать всё.

## Где держать круглосуточно

Компьютер жечь не обязательно: радар умеет работать и «слушателем» (процесс висит), и разовыми
проходами по расписанию (`--once`). Разбор вариантов — бесплатных и платных, с ценами и
подводными камнями (Cloudflare Containers, Oracle Always Free, телефон с Termux, GitHub Actions,
VPS) — в **HOSTING.md**. Пошаговый деплой в Cloudflare (Worker + контейнер + R2, схема B) —
в **DEPLOY.md**.

## Если что-то не работает

* `Cannot find any entity` — на этот чат аккаунт не подписан, опечатка в username или
  чат приватный: подставь `-100…` id (узнать у @userinfobot) либо ссылку `https://t.me/...`.
* `SessionPasswordNeededError` — включена 2FA: скрипт спросит пароль (для серврных запусков
  используй `StringSession` в env).
* `ChannelPrivateError` / `ChatAdminRequiredError` — нет доступа к истории, читать можно только новые сообщения.
* Ничего не находит, хотя объявления есть: проверь `python3 matcher.py --text "<текст сообщения>" --explain`,
  затем уменьши `min_score` на 1 и перезапусти `selftest_monitor.py`, чтобы не поймать мусор.
* Хочешь, чтобы совпадения приходили в тот же чат, где объявление, — не нужно: ссылка в
  уведомлении открывает нужное сообщение в один тап.
